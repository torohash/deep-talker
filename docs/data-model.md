# セッションとデータの配置方針

この文書は現在の実装と、その設計判断を説明する。

## セッションをどう識別するか

端末を識別する仕組みはない。ブラウザが送るCookieのトークンをハッシュ化し、`sessions.token_hash`と照合する。
IPアドレス、User-Agent、端末IDからセッションを選ぶ処理は実装していない。

1人につき1つのセッションだけを持つ。`sessions`の主キーは`user_id`で、ログインのたびにその行を新しいトークンで置き換える。

| 操作・状態                                                     | 現在の扱い                                                                                       |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 有効なCookieを持ってページを開く                               | 既存セッションを使い、その行の有効期限を28日後へ更新する                                         |
| 別の端末でログインする                                         | 同じ行を新しいトークンで上書きする。前の端末は次の操作で401になり、接続中のWebSocketも4401で切る |
| ログアウトせずスマホの画面を閉じ、Cookieが残った状態で再訪する | 同じトークン・同じセッションを使う                                                               |
| Cookieが消えた、または期限が切れた                             | IDとパスワードでのログインを求める。成功後は同じ行を置き換える                                   |
| ログアウトする                                                 | リクエストのCookieに対応する行を削除し、そのトークンを使うWS接続を閉じる                         |
| ログアウト後に同じ端末でログインする                           | 新しいトークンで同じ行を置き換える                                                               |

通常の画面では、有効なCookieがある場合にID・パスワードの再入力を求めない。
ただし、`POST /api/login`は毎回新しいトークンを発行する。既存のトークンを返すことはできない（DBにはハッシュしか保存していないため）。

### 1人1セッションにした理由

端末ごとに独立したセッションを持たせる設計も取れる。その場合、片方だけをログアウトさせられる。
OWASPの同時セッションのテスト手順は、同時セッションを許す場合に「アクティブセッションの管理、セッションの終了、新規セッションの通知」といった制御を求めている。

このアプリには端末名の記録も、セッション一覧や個別失効の画面もない。複数持てても、どの行がどの端末かを区別できず、できるのは「そのユーザーの全セッション削除」だけになる。
そこで、最初から1人1セッションにして、ログインのたびに前のトークンを置き換える。

- 行数は人数を超えないため、期限切れの行が溜まらない。
- 端末を1つだけ失効させることはできない。ログアウトは、そのユーザーの全端末に効く。
- 借りた端末を消し忘れても、次にどこかでログインすれば前のトークンは使えなくなる。

## データの置き場所

| データ           | 置き場所 | 理由                                                    |
| ---------------- | -------- | ------------------------------------------------------- |
| `users`          | Turso    | 運用者がSQLで登録する。ログイン時のパスワード照合で読む |
| `topics`         | Turso    | 運用者がSQLで登録・編集する。日時はトリガーで記録する   |
| `sessions`       | Turso    | ログイン状態                                            |
| `rounds`         | Turso    | 現在の回と、いつ何を話したかの記録                      |
| `votes`          | Turso    | 回ごとの票。休止や再起動をまたいで残す                  |
| 誰が部屋にいるか | DOの接続 | `getWebSockets()`とattachmentから求める                 |

DOのメモリは、10秒間イベントが無いと休止して消える（[Lifecycle of a Durable Object](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)）。プロセスが入れ替わるとコンストラクタから再開する。
そのため、消えて困るものはTursoに置く。逆に、接続に紐づく在室者は接続と一緒に消えればよいので、DOは接続から求めるだけで、テーブルに写しを持たない。

| 消えると困る状態           | 起きること                                       |
| -------------------------- | ------------------------------------------------ |
| 進行段階（`rounds.phase`） | トーク中に休止すると、投票中の状態に戻ってしまう |
| 当選した題材               | トーク画面に出す題材が分からなくなる             |
| 票                         | 確定済みの投票が消え、再投票になる               |
| 使用済みの題材             | 次の会議で同じ題材を使う                         |

### 回の持ち方

`rounds`の1行が、投票からトーク終了までの1回にあたる。最新の行が現在の回で、終了した行はそのまま記録として残る。同じテーブルで「いまの状態」と「いつ何を話したか」を両方持てるので、履歴専用のテーブルは設けていない。

- 次の回を始めると行が1つ増える。`rounds.id`は回の通し番号になる。
- 配信の順序を判定する番号（以前の`room_revision`）は持たない。状態はWebSocketだけで配り、接続ごとの送信順で届く。
- 誰が部屋にいるかは`room_members`のようなテーブルには持たない。接続の一覧がそのまま在室者になる。

## 題材の日時

`topics`の`created_at`・`updated_at`は、DBへの直接登録・編集という運用に合わせてDBトリガーで記録する。

- 日時を省略して登録すると、DBの時計で両方を設定する。
- 題材の通常の項目を更新すると、`created_at`を保持し、`updated_at`を更新する。
- 日時はUTCのUnixミリ秒で保存する（DB時計の秒精度）。

登録のSQLと確認手順は[本番リソースとデプロイ](resources.md#題材)を参照。
